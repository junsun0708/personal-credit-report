## 1. 프로젝트 배경 및 목적

### 1.1 배경

본 프로젝트는 **한국평가정보(KCS) Product Engineer 포지션** 지원자의 실무 역량을 평가하기 위한 사전 과제로서, 개인 사용자가 회원가입·로그인 후 본인의 **신용평가 리포트**를 조회하고 그 **조회 이력**을 관리할 수 있는 풀스택 웹 애플리케이션을 구현하는 것을 목표로 한다.

과제 안내서 분석 결과, 단순 기능 완성이 아니라 **"코드의 의도와 설계"** 를 평가하는 것이 핵심임이 명시되어 있다. 즉 다음 두 가지가 동시에 요구된다.

- **풀스택 이해도**: 인증·페이지네이션·검색·필터·정렬 로직을 **서버 측에서 처리**하는 정합성 (클라이언트 단순 필터링 불인정)
- **설계 역량**: 컴포넌트 추상화, 인증·보안 전략, 상태관리/데이터 페칭의 명확한 분리

### 1.2 목적

| 구분 | 목적 |
|---|---|
| **1차 목적** | 인증·보안(35%)을 최우선으로 한 안전한 신용정보 조회 서비스 구현 |
| **2차 목적** | 재사용 가능한 컴포넌트 설계(30%) 및 서버/클라이언트 상태 분리(25%) 시연 |
| **3차 목적** | 타입 안정성·문서화·커밋 일관성(10%)을 통한 코드 품질 입증 |
| **가산점** | Backend Option A(Spring Boot) 정상 동작으로 실무 환경 적응도 증명 |

### 1.3 기획문서 분석 결과 요약

- 평가 비중이 **인증·보안(35%) > 컴포넌트 설계(30%) > 상태관리·데이터페칭(25%) > 코드품질·문서화(10%)** 순으로, 공수 배분도 이 순서를 따른다.
- "기능 완성도보다 설계가 중요"하므로, 시간 부족 시 **완성 범위를 줄이되 구현한 부분의 품질과 README 회고를 우선**한다.
- 1차 합격 시 **코드 리뷰 인터뷰**가 진행되므로, 모든 코드는 작성자가 직접 설명 가능한 수준으로 작성한다.

## 2. 프로젝트 범위 (Scope)

### 2.1 In-Scope (포함 범위)

| 영역 | 세부 기능 | 근거 |
|---|---|---|

| **인증** | JWT Access/Refresh 토큰 발급 및 자동 재발급(FE 인터셉터) | 과제 3.1 |

| **목록** | 본인 리포트 목록 조회, 서버 페이지네이션(10건/페이지) | 과제 3.2 |
| **목록** | 검색(제목·발급기관), 필터(등급·기간), 정렬(발급일·점수) | 과제 3.2 |
| **목록** | 검색·필터·정렬 상태의 URL 쿼리 파라미터 동기화 | 과제 3.2 |
| **상세** | 리포트 ID 기반 동적 라우팅 상세 페이지 | 과제 3.3 |
| **상세** | 신용점수 시각화(게이지), 등급, 발급정보 표시 | 과제 3.3 |
| **상세** | 민감정보(주민번호 등) 마스킹, 진입 시 조회 이력 자동 기록 | 과제 3.3 |
| **이력** | 조회 이력 페이지(최신순), 중복 조회 시점 전부 기록, 페이지네이션 | 과제 3.4 |

| **문서** | README 필수 항목 + 설계 문서 9종 | 과제 5 |

### 2.2 Out-of-Scope (제외 범위)

| 제외 항목 | 사유 |
|---|---|
| 실제 신용평가사 외부 API 연동 | 과제 명시: 외부 API 사용 불가, Mock/자체 DB 제공 |
| 정교한 UI/UX 디자인, 브랜딩 | 과제 명시: 디자인 평가 별도 없음 (기본 사용성만 확보) |
| 비밀번호 재설정·이메일 인증·소셜 로그인 | 과제 요구 범위 외 (시간 제약) |
| 리포트 생성/수정/삭제(CRUD 쓰기) | 과제는 **조회** 서비스. 데이터는 시드로 주입 |
| 결제·알림·관리자 콘솔 | 과제 요구 범위 외 |
| 운영 배포(클라우드 인프라, CI/CD) | 로컬 5분 내 기동이 목표. 배포는 범위 외 |
| 멀티테넌시·조직 권한 모델 | 단일 사용자 본인 데이터 격리로 충분 |

> Out-of-Scope 항목 중 시간 여유 시 선택적으로 다룰 수 있는 후보(Optimistic Update, CSRF 토큰 추가, 테스트 커버리지)는 [[09_일정_및_WBS.md](./09_일정_및_WBS.md)]에서 별도 관리한다.

### 7.2 기능적 성공 기준 (체크리스트)

- [ ] 회원가입·로그인·로그아웃·자동 재발급이 정상 동작한다
- [ ] 미인증 사용자가 보호 라우트 접근 시 `/login`으로 리다이렉트된다
- [ ] 목록의 페이지네이션·검색·필터·정렬이 **서버에서** 처리된다
- [ ] 검색·필터·정렬 상태가 URL과 동기화되어 새로고침 시 유지된다
- [ ] 상세 진입 시 조회 이력이 자동 기록되고 민감정보가 마스킹된다
- [ ] 조회 이력이 최신순으로, 중복 시점까지 모두 표시된다
- [ ] 타인의 리포트 ID 직접 요청 시 접근이 차단된다(404/403)
- [ ] FE/BE가 README 절차대로 5분 내 기동된다

## 8. 핵심 리스크 요약 (Key Risks)

상세 분석 및 대응은 [[09_일정_및_WBS.md](./09_일정_및_WBS.md)]에서 다루며, 본 개요서는 핵심 리스크만 요약한다.

| # | 리스크 | 영향도 | 발생 가능성 | 대응 전략 |
|:---:|---|:---:|:---:|---|
| R1 | **시간 부족(8~10h)으로 전 기능 미완성** | 높음 | 높음 | 평가 비중 순 우선순위(인증>목록>상세>이력), 미구현은 README 회고에 사유 기재 |
| R2 | **Access 메모리 보관 → 새로고침 시 토큰 소실** | 중간 | 높음 | 마운트 시 silent refresh 재발급, 초기 깜빡임은 Skeleton으로 흡수 |
| R3 | **인증·보안 설계 미흡(35% 핵심)** | 높음 | 중간 | XSS(메모리/HttpOnly)·CSRF(SameSite) 대응 명시, 권한 스코프 강제 |
| R4 | **클라이언트 필터링으로 오인되는 구현** | 높음 | 중간 | 페이징/검색/필터/정렬을 JPA `Pageable`+동적쿼리로 서버 처리 |
| R5 | **H2 인메모리 재기동 시 데이터 초기화** | 낮음 | 높음 | `data.sql` 시드 자동 주입으로 데모 재현성 확보 |
| R6 | **Refresh 무효화 한계(인메모리 화이트리스트)** | 낮음 | 중간 | 한계를 README에 명시, 영속화 전환 포인트 기술 |
| R7 | **코드 리뷰 인터뷰 시 설명 불가** | 높음 | 낮음 | AI 보조 코드도 직접 이해·검증, 트레이드오프 문서화 |
