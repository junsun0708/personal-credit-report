## 1. 개요

본 문서는 개인 신용평가 리포트 조회 서비스의 백엔드 데이터베이스 설계를 정의한다.

### 1.1 기술 환경

| 항목 | 선택 | 비고 |
|---|---|---|
| DBMS | **H2 Database (인메모리 모드)** | `jdbc:h2:mem:credit;DB_CLOSE_DELAY=-1` — 실행 편의성(5분 내 기동), 시드 자동 주입 |
| ORM | **Spring Data JPA / Hibernate 6** | 엔티티 중심 도메인 모델, `Pageable` 기반 서버 페이징 내장 |
| DDL 모드 | `spring.jpa.hibernate.ddl-auto=create` | 기동 시 스키마 자동 생성 → `data.sql` 시드 주입 |
| 마이그레이션 | 미적용 (H2 인메모리) | 운영 전환 시 Flyway/Liquibase 도입 포인트만 명시 |

### 1.2 네이밍 전략

- **물리 네이밍**: Hibernate 기본 `CamelCaseToUnderscoresNamingStrategy` 적용
  - 엔티티 `CreditReport` → 테이블 `credit_report`
  - 필드 `creditScore` → 컬럼 `credit_score`
- **테이블명**: 단수형 snake_case (`user`, `credit_report`, `view_history`)
- **PK**: `id` (단일 컬럼, `BIGINT AUTO_INCREMENT`)
- **FK**: `{참조테이블}_id` 형식 (`user_id`, `report_id`)
- **시각 컬럼**: `created_at`, `viewed_at` 등 `_at` 접미사 (`TIMESTAMP`)
- **예약어 충돌**: `user`는 H2 예약어이므로 DDL에서 `"user"` 따옴표 처리(또는 `users` 매핑 고려). 본 설계는 `@Table(name = "users")`로 회피한다.

> H2 예약어 회피를 위해 **엔티티 `User` → 물리 테이블 `users`** 로 매핑한다. 이하 명세는 물리 테이블명 `users` 기준.

## 2. ERD (Entity Relationship Diagram)

```
┌──────────────────────────┐
│          users           │   회원
├──────────────────────────┤
│ PK  id           BIGINT  │
│ UQ  email        VARCHAR │
│     password     VARCHAR │
│     created_at   TIMESTAMP│
└──────────────────────────┘
        │ 1
        │
        │ 소유 (owns)
        │
        │ N
┌──────────────────────────┐
│      credit_report       │   신용평가 리포트
├──────────────────────────┤
│ PK  id           BIGINT  │
│ FK  user_id      BIGINT  │──┐
│     title        VARCHAR │  │
│     institution  VARCHAR │  │
│     credit_score INT     │  │
│     credit_grade INT     │  │
│     ssn          VARCHAR │  │   (저장: 평문/암호화, 응답: 마스킹)
│     issued_date  DATE    │  │
│     ... (상세항목)       │  │
│     created_at   TIMESTAMP│  │
└──────────────────────────┘  │
        │ 1                    │
        │                      │
        │ 조회됨 (is viewed)   │
        │                      │
        │ N                    │
┌──────────────────────────┐  │
│       view_history       │  │   조회 이력
├──────────────────────────┤  │
│ PK  id           BIGINT  │  │
│ FK  user_id      BIGINT  │──┘  (조회한 사용자)
│ FK  report_id    BIGINT  │     (조회된 리포트)
│     viewed_at    TIMESTAMP│
└──────────────────────────┘

[관계 / 카디널리티]
  users (1) ──────< (N) credit_report   : 한 회원은 0..N개의 리포트를 소유
  users (1) ──────< (N) view_history    : 한 회원은 0..N건의 조회 이력을 가짐
  credit_report (1) ──< (N) view_history : 한 리포트는 0..N건의 조회 이력으로 기록됨

  ※ view_history 는 users 와 credit_report 사이의 조회 행위(M:N)를
    "시점(viewed_at)"을 가진 연결 엔티티로 분해한 형태.
    동일 (user, report) 조합도 매 조회 시점마다 별도 행(row)으로 INSERT.
```

### 2.1 관계 요약표

| 부모 | 자식 | 관계 | 카디널리티 | 삭제 정책 |
|---|---|---|---|---|
| users | credit_report | 소유 | 1 : N | `ON DELETE CASCADE` (회원 탈퇴 시 리포트 삭제) |
| users | view_history | 조회 주체 | 1 : N | `ON DELETE CASCADE` |
| credit_report | view_history | 조회 대상 | 1 : N | `ON DELETE CASCADE` |

## 3. 테이블 명세

### 3.1 `users` — 회원

| 컬럼명 | 타입 | PK/FK | NULL | 제약 | 설명 |
|---|---|:--:|:--:|---|---|
| id | BIGINT | PK | N | AUTO_INCREMENT | 회원 식별자 |
| email | VARCHAR(255) | | N | UNIQUE | 로그인 ID (이메일 형식) |
| password | VARCHAR(60) | | N | | BCrypt 해시 (60자 고정) |
| created_at | TIMESTAMP | | N | DEFAULT CURRENT_TIMESTAMP | 가입 일시 |

- **JPA 매핑**: `@Entity @Table(name = "users")`, `email`은 `@Column(unique = true)`
- **보안**: `password`는 절대 평문 저장 금지(BCrypt 단방향 해시). API 응답 DTO에 포함하지 않음.

### 3.2 `credit_report` — 신용평가 리포트

| 컬럼명 | 타입 | PK/FK | NULL | 제약 | 설명 |
|---|---|:--:|:--:|---|---|
| id | BIGINT | PK | N | AUTO_INCREMENT | 리포트 식별자 |
| user_id | BIGINT | FK → users.id | N | INDEX | 소유 회원 (권한 격리 기준) |
| title | VARCHAR(200) | | N | | 리포트 제목 (검색 대상) |
| institution | VARCHAR(100) | | N | | 발급기관명 (검색 대상) |
| credit_score | INT | | N | CHECK (0~1000) | 신용점수 (NICE식 0~1000 가정) |
| credit_grade | INT | | N | CHECK (1~10) | 신용등급 (1=최우량 ~ 10=최저) |
| ssn | VARCHAR(14) | | N | | 주민등록번호 (응답 시 마스킹, §6 참조) |
| issued_date | DATE | | N | INDEX | 발급일자 (필터·정렬 대상) |
| report_summary | VARCHAR(1000) | | Y | | 리포트 요약/총평 |
| delinquency_count | INT | | N | DEFAULT 0 | 연체 건수 (상세 시각화) |
| total_debt | BIGINT | | N | DEFAULT 0 | 총 부채액(원) |
| credit_card_count | INT | | N | DEFAULT 0 | 보유 신용카드 수 |
| loan_count | INT | | N | DEFAULT 0 | 대출 건수 |
| created_at | TIMESTAMP | | N | DEFAULT CURRENT_TIMESTAMP | 생성 일시 |

- **등급 의미**: `credit_grade` 1~10등급. 점수 구간을 등급으로 매핑(예: 900~1000 → 1등급). 시드에서 점수·등급 정합성 유지.
- **검색 대상**: `title`, `institution` (LIKE 부분 일치, 서버 측 처리).
- **필터 대상**: `credit_grade`(등급), `issued_date`(from~to 기간).
- **정렬 대상**: `issued_date`, `credit_score` (오름/내림차순).

### 3.3 `view_history` — 조회 이력

| 컬럼명 | 타입 | PK/FK | NULL | 제약 | 설명 |
|---|---|:--:|:--:|---|---|
| id | BIGINT | PK | N | AUTO_INCREMENT | 이력 식별자 |
| user_id | BIGINT | FK → users.id | N | INDEX | 조회한 회원 |
| report_id | BIGINT | FK → credit_report.id | N | INDEX | 조회된 리포트 |
| viewed_at | TIMESTAMP | | N | DEFAULT CURRENT_TIMESTAMP | 조회 시점 |

- **중복 조회 정책**: 동일 `(user_id, report_id)` 조합이라도 상세 진입 시마다 **새 행 INSERT**. UNIQUE 제약 없음(과제 요구: 각 시점 모두 기록).
- **정렬**: 이력 페이지는 `viewed_at DESC` (최신순) + 페이지네이션.

## 4. 인덱스 설계

검색·필터·정렬 컬럼을 기준으로 인덱스를 정의한다. 권한 격리상 모든 도메인 쿼리는 `user_id`로 스코프되므로 `user_id`를 선두로 한 복합 인덱스가 핵심이다.

| 인덱스명 | 테이블 | 컬럼 | 유형 | 목적 |
|---|---|---|---|---|
| `uq_users_email` | users | (email) | UNIQUE | 로그인 조회 + 이메일 중복 방지 |
| `idx_report_user` | credit_report | (user_id) | NON-UNIQUE | 권한 격리 기본 조회 (`WHERE user_id = ?`) |
| `idx_report_user_issued` | credit_report | (user_id, issued_date) | 복합 | 본인 리포트 + 발급일 필터/정렬 |
| `idx_report_user_score` | credit_report | (user_id, credit_score) | 복합 | 본인 리포트 + 점수 정렬 |
| `idx_report_user_grade` | credit_report | (user_id, credit_grade) | 복합 | 본인 리포트 + 등급 필터 |
| `idx_history_user_viewed` | view_history | (user_id, viewed_at DESC) | 복합 | 본인 이력 최신순 페이징 |
| `idx_history_report` | view_history | (report_id) | NON-UNIQUE | 리포트별 이력 집계(FK 조인) |

### 4.1 설계 근거

- **선두 컬럼 = `user_id`**: 모든 목록/이력 쿼리가 `WHERE user_id = :currentUserId`로 시작하므로 복합 인덱스 선두에 배치 → 선택도(selectivity) 극대화.
- **정렬 컬럼 후행 배치**: `(user_id, issued_date)`, `(user_id, credit_score)`로 필터 후 정렬을 인덱스 스캔으로 해결(filesort 회피).
- **`title`/`institution` LIKE**: 부분 일치(`%q%`)는 인덱스 활용이 어려워 별도 인덱스 미부여(데이터 25~30건 규모로 영향 미미). 대용량 전환 시 Full-Text 인덱스 검토.

## 5. 제약조건 및 무결성

### 5.1 키 제약

| 종류 | 대상 | 정의 |
|---|---|---|
| PRIMARY KEY | 전 테이블 `id` | AUTO_INCREMENT 단일 PK |
| UNIQUE | `users.email` | 이메일 중복 가입 차단 |
| FOREIGN KEY | `credit_report.user_id` → `users.id` | 고아 리포트 방지, `ON DELETE CASCADE` |
| FOREIGN KEY | `view_history.user_id` → `users.id` | `ON DELETE CASCADE` |
| FOREIGN KEY | `view_history.report_id` → `credit_report.id` | `ON DELETE CASCADE` |

### 5.2 CHECK 제약

| 컬럼 | 조건 | 설명 |
|---|---|---|
| `credit_report.credit_grade` | `BETWEEN 1 AND 10` | 등급 범위 보장 |
| `credit_report.credit_score` | `BETWEEN 0 AND 1000` | 점수 범위 보장 |
| `credit_report.delinquency_count` | `>= 0` | 음수 방지 |

### 5.3 권한 격리(Row-level) 쿼리 원칙

> **본인 데이터만 조회** — 평가 항목 "API 권한 검증" 직접 대응.

- DB 레벨 RLS는 사용하지 않고 **애플리케이션 레벨에서 강제**한다.
- 모든 도메인 Repository 쿼리는 인증 컨텍스트의 `currentUserId`를 **필수 조건**으로 포함한다.

```java
// 목록: 항상 user_id 스코프
Page<CreditReport> findAllByUserId(Long userId, Specification<CreditReport> spec, Pageable pageable);

// 상세: id 단독 조회 금지 → (id, userId) 동시 조건
Optional<CreditReport> findByIdAndUserId(Long id, Long userId);
// → 타인 리포트 id 직접 요청 시 empty → 404/403 응답
```

- **금지 패턴**: `findById(id)` 단독 사용(권한 누수). 반드시 `userId` 결합.

## 6. 민감정보 처리 — 주민등록번호

### 6.1 저장 전략

| 구분 | 방식 | 비고 |
|---|---|---|
| 저장 컬럼 | `credit_report.ssn` VARCHAR(14) | `YYMMDD-XXXXXXX` 형식(13자리+하이픈) |
| 저장 형태(과제 기준) | **평문 저장** 허용 | 외부 API·실데이터 없는 과제 특성. README에 트레이드오프 명시 |
| 운영 권장(확장 포인트) | AES-256 양방향 암호화 후 저장 | 키는 환경변수/KMS 관리. 본 과제 범위 외 |

### 6.2 마스킹 전략 — **서버 응답 단계 마스킹**

> 평문이 네트워크로 절대 노출되지 않도록 **응답 DTO 생성 시점**에 마스킹한다. (클라이언트 마스킹 금지 — 원본이 전송되면 무의미)

- **마스킹 규칙**: 생년월일 6자리 + 성별 1자리만 노출, 나머지 6자리 `*` 치환
- **예시**: `900101-1234567` → **`900101-1******`**

```java
// 서버: 엔티티 → 응답 DTO 변환 시 마스킹
public static String maskSsn(String ssn) {
    // "900101-1234567" -> "900101-1******"
    if (ssn == null || ssn.length() < 8) return "******";
    return ssn.substring(0, 8) + "******"; // 앞 8자(YYMMDD-G) + 6 별표
}
```

- **적용 지점**: `ReportDetailResponse` DTO 빌드 시. 엔티티 원본 `ssn`은 응답 직렬화 대상에서 제외(`@JsonIgnore` 또는 DTO 미포함).
- **로깅 금지**: `ssn` 평문이 로그/예외 메시지에 출력되지 않도록 주의.

## 7. 시드 데이터 전략

`backend/src/main/resources/data.sql` 로 기동 시 자동 주입한다. (`spring.jpa.hibernate.ddl-auto=create` → schema 생성 후 `data.sql` 실행)

### 7.1 구성

| 항목 | 수량 | 설명 |
|---|---|---|
| 테스트 계정 | 1개 | `test@kcs.com` / 비밀번호 `Test1234!`(BCrypt 해시 저장) |
| 신용평가 리포트 | **25~30건** | 페이지네이션(10/page → 3페이지)·필터·정렬 검증용 |

### 7.2 데이터 분산 설계

> 목록의 검색·필터·정렬을 모두 시연하려면 값이 골고루 분산되어야 한다.

| 분산 축 | 설계 |
|---|---|
| `credit_grade` | 1~10등급을 고르게 분포 (각 등급 2~3건) → 등급 필터 검증 |
| `issued_date` | 최근 2~3년에 걸쳐 분산 (월별 분포) → 기간 필터 + 발급일 정렬 검증 |
| `credit_score` | 등급과 정합되게 분산 (예: 1등급 ≈ 950, 10등급 ≈ 350) → 점수 정렬 검증 |
| `institution` | NICE평가정보 / KCB / 한국평가정보 등 3~4개 → 발급기관 검색 검증 |
| `title` | "2024 상반기 신용리포트" 등 키워드 분산 → 제목 검색 검증 |
| `ssn` | 마스킹 시연용 더미 주민번호 (실 데이터 아님) |

### 7.3 시드 SQL 예시 (발췌)

```sql
-- 테스트 계정 (비밀번호 'Test1234!' 의 BCrypt 해시)
INSERT INTO users (email, password, created_at) VALUES
  ('test@kcs.com', '$2a$10$abcdefghijklmnopqrstuvCghI...해시...', CURRENT_TIMESTAMP);

-- 리포트 시드 (user_id = 1 가정, 등급/발급일/점수 분산 — 총 25~30건)
INSERT INTO credit_report
  (user_id, title, institution, credit_score, credit_grade, ssn, issued_date,
   report_summary, delinquency_count, total_debt, credit_card_count, loan_count, created_at)
VALUES
  (1, '2024 상반기 신용리포트', 'NICE평가정보', 952, 1, '900101-1234567', '2024-01-15',
   '우량 등급. 연체 이력 없음.', 0, 0, 2, 0, CURRENT_TIMESTAMP),
  (1, '2024 하반기 신용리포트', 'KCB',          720, 4, '850315-2234567', '2024-07-20',
   '중위 등급. 카드 사용 양호.', 0, 12000000, 3, 1, CURRENT_TIMESTAMP),
  (1, '2023 연말 신용리포트',  '한국평가정보',  410, 9, '920808-1234567', '2023-12-05',
   '주의 등급. 연체 이력 존재.', 2, 35000000, 1, 3, CURRENT_TIMESTAMP);
  -- ... (총 25~30건, 등급 1~10 및 발급일 분산하여 추가)
```

> 시드 작성 실무 팁: 25~30건은 SQL 직접 나열보다 **데이터 생성 규칙(등급별 점수 범위, 발급일 월 분산)** 을 정해두고 일괄 생성하면 정합성 유지가 쉽다.

## 8. DDL 예시 (H2 호환)

```sql
-- ============================================================
-- users : 회원
-- ============================================================
CREATE TABLE users (
    id          BIGINT       AUTO_INCREMENT PRIMARY KEY,
    email       VARCHAR(255) NOT NULL,
    password    VARCHAR(60)  NOT NULL,
    created_at  TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uq_users_email UNIQUE (email)
);

-- ============================================================
-- credit_report : 신용평가 리포트
-- ============================================================
CREATE TABLE credit_report (
    id                 BIGINT        AUTO_INCREMENT PRIMARY KEY,
    user_id            BIGINT        NOT NULL,
    title              VARCHAR(200)  NOT NULL,
    institution        VARCHAR(100)  NOT NULL,
    credit_score       INT           NOT NULL,
    credit_grade       INT           NOT NULL,
    ssn                VARCHAR(14)    NOT NULL,
    issued_date        DATE          NOT NULL,
    report_summary     VARCHAR(1000),
    delinquency_count  INT           NOT NULL DEFAULT 0,
    total_debt         BIGINT        NOT NULL DEFAULT 0,
    credit_card_count  INT           NOT NULL DEFAULT 0,
    loan_count         INT           NOT NULL DEFAULT 0,
    created_at         TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_report_user
        FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE,
    CONSTRAINT chk_credit_grade CHECK (credit_grade BETWEEN 1 AND 10),
    CONSTRAINT chk_credit_score CHECK (credit_score BETWEEN 0 AND 1000),
    CONSTRAINT chk_delinquency  CHECK (delinquency_count >= 0)
);

CREATE INDEX idx_report_user        ON credit_report (user_id);
CREATE INDEX idx_report_user_issued ON credit_report (user_id, issued_date);
CREATE INDEX idx_report_user_score  ON credit_report (user_id, credit_score);
CREATE INDEX idx_report_user_grade  ON credit_report (user_id, credit_grade);

-- ============================================================
-- view_history : 조회 이력
-- ============================================================
CREATE TABLE view_history (
    id          BIGINT     AUTO_INCREMENT PRIMARY KEY,
    user_id     BIGINT     NOT NULL,
    report_id   BIGINT     NOT NULL,
    viewed_at   TIMESTAMP  NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_history_user
        FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE,
    CONSTRAINT fk_history_report
        FOREIGN KEY (report_id) REFERENCES credit_report (id) ON DELETE CASCADE
);

CREATE INDEX idx_history_user_viewed ON view_history (user_id, viewed_at);
CREATE INDEX idx_history_report      ON view_history (report_id);
```

> **참고**: Hibernate `ddl-auto=create` 사용 시 위 DDL은 엔티티 매핑으로부터 자동 생성된다. 본 스니펫은 스키마 검증·문서화 목적의 명시적 표현이며, H2 문법 기준으로 작성되었다. CHECK·인덱스를 엔티티 어노테이션(`@Check`, `@Table(indexes=...)`)으로 선언하면 자동 생성 DDL에 반영된다.

## 9. 테이블 ↔ API 매핑

테이블이 어떤 API에서 사용되는지 매핑은 별도 문서를 참조한다.

| 테이블 | 주요 사용 API | 비고 |
|---|---|---|
| users | `POST /api/auth/signup`, `POST /api/auth/login` | 상세는 [05_API_명세서.md] 참조 |

| view_history | `GET /api/reports/{id}` (INSERT), `GET /api/histories` | 상세 진입 시 기록, 이력 조회 |

> 엔드포인트별 요청/응답 스키마, 페이지네이션 파라미터, 에러 포맷은 **[05_API_명세서.md]** 를 참조한다.
