## 1. 아키텍처 개요

### 1.1 목표

이메일/비밀번호 인증을 통과한 사용자가 **본인의 신용평가 리포트**를 목록 조회(서버 페이징·검색·필터·정렬), 상세 조회(점수 시각화·민감정보 마스킹), 조회 이력 관리까지 수행하는 풀스택 웹 애플리케이션을 구현한다. 백엔드는 가산점 옵션인 **Spring Boot 3.x (Option A)** 로 구성한다.

본 아키텍처는 다음 두 가지를 핵심 설계 원칙으로 삼는다.

- **인증·보안 우선 (평가 비중 35%)** — Access(메모리) / Refresh(HttpOnly Cookie) 분리 토큰 전략, Spring Security 필터 체인, 401 자동 재발급.
- **서버 측 데이터 처리 강제** — 페이지네이션·검색·필터·정렬은 전부 서버에서 처리한다. 클라이언트 단순 필터링은 과제 요건상 인정되지 않는다.

### 1.2 품질 속성 (Quality Attributes)

| 품질 속성 | 목표 | 아키텍처적 달성 수단 |
|---|---|---|
| 보안 (Security) | XSS/CSRF 노출면 최소화, 본인 데이터 격리 | Access=메모리·Refresh=HttpOnly 쿠키, 쿼리 단위 `user_id` 스코프 강제, 서버 측 마스킹 |
| 유지보수성 (Maintainability) | 계층 책임 분리, 관심사 분리 | Controller→Service→Repository 3계층, FE ui/domain/layout 분리 |
| 실행 편의성 (Operability) | 5분 내 로컬 기동 | H2 인메모리 + `data.sql` 시드 자동 주입, `.env` 기반 환경설정 |
| 일관성 (Consistency) | 응답·에러 포맷 통일 | 표준 응답 래퍼, `@RestControllerAdvice` 전역 에러 처리 |
| 테스트 용이성 (Testability) | 계층 단위 검증 | 인터페이스 기반 의존성, 순수 Service 로직 분리 |
| 성능 (Performance) | 불필요 재요청 최소화 | TanStack Query 캐싱(staleTime/gcTime), queryKey 조합 캐시 |

### 1.3 아키텍처 스타일

- **물리적**: 클라이언트(SPA형 Next.js) ↔ REST API 서버(Spring Boot)의 2-tier(+DB) 분리 구조.
- **논리적**: 프론트는 관심사 기반 계층(presentation/state/data-access), 백엔드는 고전적 레이어드 아키텍처(Controller / Service / Repository / Domain).

### 2.2 백엔드 계층별 책임 (Controller → Service → Repository)

| 계층 | 책임 | 하지 않는 것 |
|---|---|---|
| **Controller** | HTTP 요청/응답 변환, DTO 바인딩·검증(`@Valid`), HTTP status 결정, 표준 응답 래핑, 인증 주체(`@AuthenticationPrincipal`) 추출 | 비즈니스 규칙, 직접 DB 접근, 트랜잭션 관리 |
| **Service** | 비즈니스 규칙, 트랜잭션 경계(`@Transactional`), 권한 스코프(`user_id`) 강제, 민감정보 마스킹, 도메인 ↔ DTO 변환 오케스트레이션 | HTTP 의존(Request/Response 직접 참조 금지), SQL 직접 작성 |
| **Repository** | 영속화 추상화(Spring Data JPA), `Pageable` 페이징, `Specification` 동적 쿼리(검색/필터/정렬) | 비즈니스 판단, 권한 결정(파라미터로 받은 스코프만 적용) |
| **Domain (Entity)** | 도메인 상태·불변식 표현, 연관관계 정의 | 외부 계층 의존 |

> **권한 격리 원칙**: 모든 도메인 조회는 Service 계층에서 현재 인증 사용자의 `user_id`를 쿼리 조건으로 강제 주입한다. 타인의 리포트 ID를 직접 요청해도 결과가 비어 404가 반환된다.

### 2.3 프론트엔드 계층별 책임

| 계층 | 책임 |
|---|---|
| **Presentation** (`app/`, `components/`) | 라우팅, 화면 구성, 보호 라우트 가드, 로딩/에러/빈 상태 렌더링 |
| **State** (Zustand) | 클라이언트 전역 상태(accessToken 메모리 보관, user) |
| **Data-Access** (TanStack Query + Axios) | 서버 상태 페칭·캐싱·invalidation, queryKey 설계, 인터셉터 기반 토큰 부착·재발급 |

> **상태 분리 원칙**: 서버 상태(리포트·이력)는 TanStack Query, 클라이언트 상태(인증)는 Zustand로 명확히 분리한다(평가 항목 25%).

## 4. 기술 스택 결정 근거 (ADR)

> 형식: 결정(Decision) / 대안(Alternatives) / 이유(Rationale)

| # | 결정 | 대안 | 이유 |
|---|---|---|---|
| ADR-01 | **Backend = Spring Boot 3.x (Option A)** | Next.js Route Handler (Option B, Mock) | 과제 가산점 명시. 실무 협업 환경(Java+Spring) 재현으로 업무 적응도 어필. Spring Security 필터 체인으로 인증 흐름(35% 비중)을 명시적 설계 가능 |
| ADR-02 | **DB = H2 In-Memory** | MySQL, SQLite | "5분 내 기동" 실행 편의성. 시드 자동 주입으로 데모 일관성. 운영 전환 시 MySQL 포인트만 README 명시 |
| ADR-03 | **클라이언트 상태 = Zustand** | Redux Toolkit, Context API | 인증 토큰·유저만 전역 필요 → 보일러플레이트 최소·경량. 과제 권장 스택 |
| ADR-04 | **서버 상태 = TanStack Query** | SWR, 직접 fetch + useState | 캐싱(staleTime/gcTime)·로딩/에러/빈 상태·invalidation 일원화. queryKey 조합 캐시로 평가 항목(25%) 충족 |
| ADR-05 | **토큰 저장 = Access(메모리) / Refresh(HttpOnly Cookie)** | 둘 다 localStorage, 둘 다 쿠키 | Access는 메모리로 XSS 노출면 제거, Refresh는 JS 접근 불가 쿠키로 탈취 방어. 보안 항목 최우선 대응 |
| ADR-06 | **ORM = Spring Data JPA + Specification** | MyBatis, 순수 JDBC | 엔티티 중심 도메인 모델, `Pageable` 페이징 내장, Specification으로 동적 검색/필터/정렬을 서버에서 안전하게 조립 |
| ADR-07 | **스타일링 = Tailwind CSS + shadcn/ui** | MUI, 직접 CSS | 디자인 시스템으로 공통 UI 컴포넌트 추상화 가속(30% 비중). 코드 소유 기반(headless)으로 커스터마이즈 자유 |
| ADR-08 | **폼/검증 = react-hook-form + zod** | Formik, 수동 검증 | 클라이언트 검증과 타입 추론 일치. 비밀번호 정책을 서버(BCrypt 저장 전 검증)와 미러링 |
| ADR-09 | **API 문서 = springdoc-openapi (Swagger UI)** | 수기 문서만 | README 요구 "API 명세" 자동 충족, FE-BE 인터페이스 계약 동기화 |
| ADR-10 | **빌드 = Gradle** | Maven | 의존성 선언 간결, Spring 생태계 표준 |

## 5. 인증 아키텍처

### 5.1 토큰 전략 요약

| 토큰 | 만료 | 저장 위치 | 전송 방식 | 보안 의도 |
|---|---|---|---|---|
| Access Token | 15분(짧음) | 메모리(Zustand) | `Authorization: Bearer` 헤더 | XSS 노출면 최소화 (localStorage 미사용) |
| Refresh Token | 7일(김) | HttpOnly + Secure + SameSite 쿠키 | 쿠키 자동 전송 | JS 접근 차단(XSS 방어), CSRF 표면 축소 |

### 5.2 로그인 → 토큰 발급 시퀀스

```
 [Browser/FE]            [Next.js UI]         [Spring Security]        [AuthService/DB]
     │                        │                       │                       │
     │ 이메일·비번 입력        │                       │                       │
     ├───────────────────────▶│                       │                       │
     │                        │ POST /api/auth/login  │                       │
     │                        ├──────────────────────▶│                       │
     │                        │                       │ 자격증명 검증 요청     │
     │                        │                       ├──────────────────────▶│
     │                        │                       │                       │ BCrypt.matches()
     │                        │                       │                       │ Access·Refresh 생성
     │                        │                       │◀──────────────────────┤
     │                        │  200 OK               │                       │
     │                        │  body: { accessToken }│                       │
     │                        │  Set-Cookie: refresh  │                       │
     │                        │   (HttpOnly;Secure;   │                       │
     │                        │    SameSite=Strict)   │                       │
     │                        │◀──────────────────────┤                       │
     │ Access → 메모리 저장    │                       │                       │
     │ Refresh → 쿠키(JS 불가) │                       │                       │
     │◀───────────────────────┤                       │                       │

```

### 5.3 Spring Security 필터 체인

```
요청
  │
  ▼
┌─────────────────────┐
│ CorsFilter          │  허용 출처(localhost:3000)·자격증명(쿠키) 검사
└─────────┬───────────┘
          ▼
┌─────────────────────┐
│ JwtAuthentication   │  Authorization 헤더에서 Access 추출 → 서명·만료 검증
│ Filter (커스텀)     │  유효 시 SecurityContext에 인증 주체 설정
└─────────┬───────────┘
          ▼
┌─────────────────────┐
│ Authorization 판단  │  SecurityFilterChain 규칙:
│                     │   - /api/auth/signup, /login, /refresh : permitAll
│                     │   - 그 외 /api/**                       : authenticated
└─────────┬───────────┘
          ▼
┌─────────────────────┐
│ ExceptionTranslation│  인증 실패 → 401, 권한 실패 → 403
│ + EntryPoint        │  (표준 에러 포맷 { code, message } 반환)
└─────────┬───────────┘
          ▼
   Controller 진입
```

### 5.4 401 → Access 자동 재발급 시퀀스 (FE 인터셉터)

```
 [TanStack Query]      [Axios Interceptor]        [Spring Boot]
       │                      │                        │
       │ GET /api/reports     │                        │
       │ (Bearer 만료 Access) │                        │
       ├─────────────────────▶│ 요청 전송               │
       │                      ├───────────────────────▶│
       │                      │                        │ Access 만료 검증
       │                      │   401 Unauthorized      │
       │                      │◀───────────────────────┤
       │                      │                        │
       │           ┌──────────┴───────────┐            │
       │           │ 401 감지 → refresh 분기 │            │
       │           │ (동시 401 다발 시       │            │
       │           │  refresh 단일화·큐잉)   │            │
       │           └──────────┬───────────┘            │
       │                      │ POST /api/auth/refresh  │
       │                      │ (Refresh 쿠키 자동 전송)│
       │                      ├───────────────────────▶│
       │                      │                        │ Refresh 검증
       │                      │   200 { newAccess }     │ 새 Access 발급
       │                      │◀───────────────────────┤
       │                      │ 메모리 Access 갱신       │
       │                      │ ┌─ 원요청 재시도 ──────┐│
       │                      │ │ GET /api/reports     ││
       │                      │ │ (새 Bearer)          ││
       │                      │ ├─────────────────────▶││
       │                      │ │   200 OK { data }    ││
       │                      │ │◀─────────────────────┤│
       │ 정상 응답 수신        │ └──────────────────────┘│
       │◀─────────────────────┤                        │
       │                      │                        │
       │   ※ refresh 자체가 401 → 세션 만료 →          │
       │     Zustand 초기화 + /login 리다이렉트         │
```

- **동시성 처리**: 다수 요청이 동시에 401을 받아도 refresh 호출은 1회로 단일화하고, 나머지 요청은 새 Access 발급 완료까지 큐에서 대기 후 재시도한다(중복 재발급 방지).
- **재발급 실패**: refresh 자체가 만료/무효(401)면 인증 상태를 초기화하고 로그인 페이지로 리다이렉트한다.

### 5.5 로그아웃 / 토큰 무효화

```
FE: POST /api/auth/logout (Bearer + Refresh 쿠키)
      │
      ▼
BE: Refresh 무효화(서버 화이트리스트 제거) + Set-Cookie 만료(쿠키 삭제 지시)
      │
      ▼
FE: Zustand accessToken·user 초기화 → /login 이동
```

> 인메모리 Refresh 화이트리스트로 로그아웃을 처리하며, 서버 재기동 시 초기화되는 한계는 README 회고에 명시한다.

## 6. 데이터 흐름

### 6.1 리포트 목록 조회 흐름 (서버 페이징·검색·필터·정렬)

```
[URL ?page=1&q=신한&grade=3&from=..&to=..&sort=issuedDate&order=desc]
   │  (useSearchParams 동기화 → 새로고침 시 상태 유지)
   ▼
TanStack Query  queryKey: ['reports', { page, q, grade, from, to, sort, order }]
   │  (조합별 캐시 / staleTime 30s · gcTime 5m)
   ▼
Axios  GET /api/reports?page&size=10&q&grade&from&to&sort&order  (Bearer)
   ▼
ReportController  쿼리 파라미터 → 검색 조건 DTO 바인딩
   ▼
ReportService  현재 user_id 스코프 강제 주입 → Specification 동적 조건 조립
   ▼
ReportRepository.findAll(spec, pageable)  ← 검색/필터/정렬/페이징 전부 서버 처리
   ▼
응답: { data: [...], page, size, totalElements, totalPages }
   ▼
FE 렌더: Table + Pagination (로딩=Skeleton / 빈 결과=EmptyState / 에러=ErrorState)
```

> 핵심: **검색·필터·정렬·페이징은 100% 서버 처리**. 클라이언트는 결과를 표시만 한다(과제 명시 요건).

### 6.2 리포트 상세 조회 + 이력 자동 기록 흐름

```
[/reports/123 진입]
   │
   ▼
TanStack Query  queryKey: ['report', 123]  (staleTime 5m — 상세는 거의 불변)
   ▼
Axios  GET /api/reports/123  (Bearer)
   ▼
ReportController → ReportService
   │
   ├─(1) 본인 소유 검증: WHERE id=123 AND user_id=:current  → 미일치 시 404
   │
   ├─(2) 민감정보 마스킹: ssn → 900101-1******  (서버 응답 단계에서 마스킹)
   │       └ 평문이 네트워크로 절대 나가지 않음
   │
   └─(3) 조회 이력 기록: ViewHistory INSERT (user_id, report_id, viewed_at=now)
           └ 중복 조회도 각 시점을 별도 행으로 기록
   ▼
응답: { id, title, institution, creditScore, creditGrade, issuedDate, ssn(마스킹) }
   ▼
FE 렌더: CreditScoreGauge(게이지) + GradeBadge(등급) + 마스킹 표시
   ▼
성공 시 ['histories'] invalidate → 이력 페이지 자동 갱신
```

> 이력 기록(쓰기)과 상세 조회(읽기)는 동일 트랜잭션 경계 내에서 처리한다. 상세 진입 = 이력 1건 적재가 보장된다.

## 7. 횡단 관심사 (Cross-Cutting Concerns)

### 7.1 에러 처리 (전역)

```
[Backend]
  @RestControllerAdvice (GlobalExceptionHandler)
   ├ BusinessException        → 4xx + { code, message }
   ├ MethodArgumentNotValid   → 400 (검증 실패 필드 메시지)
   ├ AuthenticationException  → 401
   ├ AccessDeniedException    → 403
   └ 그 외 Exception          → 500 (내부 상세 비노출, 로깅만)

[Frontend]
  ├ Axios 인터셉터: 401 → 재발급(§5.4) / 그 외 status → 표준 에러 throw
  ├ TanStack Query onError + ErrorBoundary: 화면 단위 ErrorState 렌더
  └ 재발급 로직과 일반 에러 처리는 책임 분리
```

- **에러 포맷 통일**: 백엔드 모든 에러 응답은 `{ code, message }` + 적절한 HTTP status로 표준화한다.

### 7.2 로깅

| 대상 | 정책 |
|---|---|
| 요청/응답 | 메서드·경로·status·소요시간 (개발 프로파일에서 상세) |
| 인증 이벤트 | 로그인 성공/실패, 토큰 재발급, 로그아웃 (PII·토큰 평문 미기록) |
| 예외 | 500 계열은 스택트레이스 포함 서버 로깅, 클라이언트에는 비노출 |
| 민감정보 | 비밀번호·토큰·주민번호 평문 **로그 금지** |

### 7.3 CORS

```
허용 출처(Origin)      : http://localhost:3000
허용 메서드            : GET, POST, (필요 시 PUT/DELETE)
허용 헤더              : Authorization, Content-Type
자격증명(credentials)  : true   ← Refresh 쿠키 송수신 필수
설정 위치              : Spring Security CorsConfigurationSource
```

> 쿠키 기반 Refresh를 사용하므로 `allowCredentials=true`이며, 와일드카드(`*`) 출처는 사용할 수 없다(명시적 출처 등록).

### 7.4 환경설정 (.env)

| 위치 | 키 | 용도 |
|---|---|---|
| frontend `.env.local` | `NEXT_PUBLIC_API_BASE_URL` | 백엔드 API Base URL |
| backend (환경변수/`application.yml`) | `JWT_SECRET` | JWT 서명 비밀키 (커밋 금지) |
| backend | `JWT_ACCESS_EXP`, `JWT_REFRESH_EXP` | 토큰 만료시간 |
| backend | `CORS_ALLOWED_ORIGIN` | 허용 출처 |

> **절대 금지**: 비밀키·`.env`는 절대 커밋하지 않는다. 저장소에는 `.env.example`만 제공한다.
